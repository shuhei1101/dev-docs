# 配信元を配信する

端末の設定と dev-docs.yaml を記載して dev-docs serve で配信し、文書の MCP で読む手順

## 手順

<!-- steps -->

1. 配信元のフォルダに `dev-docs.yaml` を置く。
   配信する文書の行を `documents[]` に記載する。
   ```yaml
   version: "3"
   name: knowledge
   description: どのプロジェクトでも使うコーディング規約
   documents:
     - id: rules
       paths: [docs/rule/*.yaml]
       title: 規約
       schema: schemas/rule.schema.yaml
   ```
2. 端末の設定 `~/.config/dev-docs/settings.yaml` に配信元の行を追加する。
   別の場所に置くときは、環境変数 `DEV_DOCS_CONFIG` でパスを渡す。
   ```yaml
   version: "1"
   clone: /home/me/repo/dev-docs
   sources:
     - id: knowledge
       config: /home/me/repo/knowledge/dev-docs.yaml
       scope:
         read: [/home/me/repo/ai-monitor/**]
         write: [/home/me/repo/knowledge]
   ```
3. サーバーを起動する。
   ```bash
   dev-docs serve
   ```
4. 標準出力に出た、配信している配信元の ID を確かめる。
5. Claude Code から `http://127.0.0.1:8781/mcp` に接続し、文書の MCP で読み書きする。

<!-- /steps -->

## Git のリポジトリを配信する

Git のリポジトリの配信元は、端末の設定の `sources[].config` にメインのリポジトリ（クローン本体）の `dev-docs.yaml` を指します。
ワークツリーの `dev-docs.yaml` は指しません。

| 読むもの | 読む場所 |
| --- | --- |
| 文書（`ref` を省いたとき） | `dev-docs.yaml` の `default_ref`（既定 `develop`）のリビジョン |
| `dev-docs.yaml`・`documents[].schema` のスキーマ・`validators`・`converters` のスクリプト | `default_ref` のリビジョン。クローン本体が別のブランチを checkout していても `default_ref` から読む |
| 作業中の文書・設定・スクリプトと、`generators` のスクリプト | `cwd` か `worktree` の引数が指すワークツリー |

`default_ref` は、ディスクにある先頭の `dev-docs.yaml` の値を使います。
サーバーは要求のたびに `default_ref` の commit を確かめ、進んでいれば配信元を組み立て直すので、`default_ref` へマージした設定は `reload` なしで配信に入ります。

作業はワークツリー（既定 `.claude/worktrees/*`）で行い、文書の MCP の読み書きもワークツリーに向けます。
`worktrees[]` の相対パスはメインのリポジトリの直下から数えます。
配信元のブランチ・タグと、`worktrees[]` に当たるワークツリーのパスと checkout しているブランチは、`describe(source)` で引けます。

## スキルで登録する

`/dev-docs:setup [path]` は、フォルダを配信元として端末の設定に登録します。
`path` を省くと、今の作業場所を対象にします。
`/dev-docs:global-setup` を済ませ、dev-docs が待ち受けている必要があります（[dev-docsを入れる](./dev-docsを入れる.md)）。

<!-- steps -->

1. 配信元に `dev-docs.yaml` があれば、`check_project` で設定のバージョンの新旧・違反・索引の同期の件数を確かめる。
   違反があれば、キーのパスと理由を示して止まる。端末の設定は書き換えない。
2. `scope.write`・`scope.read` を、既定の値つきで聞かれる。
   既定は、`scope.write` が配信元のパス、`scope.read` が `{path}/**`。
3. `dev-docs.yaml` が無い配信元（YAML でない範囲）では、範囲の glob（既定 `**/*.md`）と仮のメタデータ、実装のパスを持つ設計書の種類とキー（既定は無し）も聞かれる。
4. YAML でない範囲では、`dev-docs files` で範囲のうち載せるファイルを求める。
   範囲から `.git`・`node_modules`・`.claude/worktrees` の下のファイルと、除外の条件に当たるファイルは除く。
5. 記載する内容を表で確かめ、了承する。
   断ると、何も書き換えない。
6. YAML でない範囲では、雛形から `dev-docs.yaml` を作り、`templates/files.schema.yaml` に沿って管理用の YAML に 1 ファイル 1 行を記載する。
7. `check_project` で違反が無いことを確かめ、端末の設定の `sources[]` に行を記載する。
8. `reload` で配信を始める。
   `/mcp` のセッションは切れず、セッションを張り直さずに `describe` と `search_docs` で使える。

<!-- /steps -->

2 回目以降は、`scope`・範囲は聞かず、範囲のファイルと管理用の YAML の行を突き合わせます。
追加・削除・改名の行を表で確かめ、了承されたら `write_docs` で管理用の YAML の行を修正し、`check_project` と `reload` で確かめます。
改名は、Git の配信元では Git のリネームの検出、Git 管理外の配信元では内容のハッシュで見つけます。
改名した行は、パスだけが新しくなり、メタデータは元の値を保ちます。

管理用の YAML に行を追加するときは、確認の表に `implements`・`tests` の候補を出します。
テストのファイルには、ファイル名から `test_` の接頭辞（`_test`・`.test` の接尾辞）を除いた名前のコードを指す `tests` を付けます。
同じ名前のコードが範囲に無ければ、候補を付けません。
実装のパスを持つ設計書の種類とキー（初回は手順 3、2 回目以降は表の前に聞かれる）に答えると、その種類の文書を `search_docs` で引いて、そのキーの値とパスが一致するコードに、その設計書を指す `implements` を付けます。
既定の無しのままなら、`implements` の候補は出しません。
除外の条件に当たるファイルは、行を作りません（[文書のメタデータ](../はじめに/コアコンセプト/文書のメタデータ.md) の「載せるファイルの判定」）。

範囲のファイルを作った・削除した・改名したときに、索引へ反映するフックはありません。
そのたびに、管理用の YAML の行を修正します。

配信元の直下か、配信元の中のプラグインのルート（`.claude-plugin/plugin.json` を持つフォルダ）に `content/prompts/` があると、そのフォルダを配信する `documents[]` の行を候補に出します。
候補は、初回も 2 回目以降も、管理用の YAML の行と同じ表で確かめます。
同じ `paths` の行が既にあるフォルダは、候補に出しません。
了承すると、`templates/prompt.schema.yaml` を配信元の `schemas/` にコピーし、行と `converters[]`・`nav` の行を `dev-docs.yaml` に記載します。
記載する行は「プロンプトを配信する」にあります。

## ソースコードを配信する

ソースコードなど YAML でない文書は、管理用の YAML に記載して配信します。

<!-- steps -->

1. 配信するファイルのフォルダに、管理用の YAML `files.yaml` を置く。
   `files[]` に、配信するファイルを 1 ファイル 1 行で記載する。
   共通のタグも各行の `tags` に記載する。
   ```yaml
   files:
     - path: a.py
       tags: [code, auth]
     - path: b.py
       name: 部品 B
       tags: [code]
   ```
2. dev-docs の `templates/files.schema.yaml` を配信元のフォルダにコピーする。
3. `dev-docs.yaml` の `documents[]` に、管理用の YAML を指す行を記載する。
   ```yaml
   documents:
     - id: src
       paths: [src/files.yaml]
       schema: schemas/files.schema.yaml
       records: files
       body_file: path
   ```
4. サーバーを起動し、`search_docs` で `tags` が `auth` の文書を引く。
   `a.py` が文書 `src/a` として、`name` が `a`・`tags` が `code` と `auth` で返る。

<!-- /steps -->

`files.yaml` に記載していないファイル（除外の条件に当たるファイルを除く）と、ファイルが無い行は、起動時の警告のログに件数が残ります。
キーの一覧は [設定](../リファレンス/設定.md) の「管理用の YAML」、仕組みは [文書のメタデータ](../はじめに/コアコンセプト/文書のメタデータ.md) にあります。

## プロンプトを配信する

`content/prompts/` に置いたプロンプトの YAML（キーは `templates/prompt.schema.yaml`）は、`dev-docs prompt-doc` の変換で、変数の表・テンプレート・例のセクションを持つ文書として配信します。

<!-- steps -->

1. dev-docs の `templates/prompt.schema.yaml` を配信元の `schemas/` にコピーする。
2. `dev-docs.yaml` に、プロンプトの行と、`dev-docs prompt-doc` を呼ぶ `converters[]` の行を記載する。
   サイドバーを `kind` ごとにまとめるときは、`nav` に `group_by: kind` の `auto` を記載する。
   ```yaml
   documents:
     - id: prompts
       paths: [content/prompts/**/*.yaml]
       title: プロンプト
       schema: schemas/prompt.schema.yaml
       converter: prompt-doc
       metadata:
         name: name
         description: description
         tags: tags
   converters:
     - id: prompt-doc
       run: [dev-docs, prompt-doc]
   nav:
     tabs:
       - title: プロンプト
         items:
           - auto: {document: prompts, group_by: kind}
   ```
3. `check_project` と `reload` で配信に入れ、画面でプロンプトのタブを開く。

<!-- /steps -->

プラグインのルートの `content/prompts/` は、`paths` をそのフォルダにした行を別に記載します（`id` は行ごとに変えます）。
`converters[].run` の `dev-docs` は、PATH に無くても dev-docs を動かしている Python の環境から引きます。
出力のセクションと終了コードは [CLI](../リファレンス/CLI.md) の「dev-docs prompt-doc」にあります。

## 起動時の検証

サーバーは起動時に、各配信元の設定（マージした結果）をスキーマで検証し、検査・変換・生成のスクリプトを実行できるかを確かめます。
検証に失敗した配信元は配信せず、配信元の ID・違反したキーのパス・理由をエラーログに記録します。
ほかの配信元は配信します。

| 事象 | 動き |
| --- | --- |
| 配信元の設定がスキーマに違反する | その配信元だけを配信しない。ログは `log_dir`（既定 `~/.local/state/dev-docs/logs`）に記録する。設定の `version` が古いときは、`dev-docs migrate --source` で移し替えられることも記録する |
| 端末の設定が無い・スキーマに違反する | 標準エラーに `{ファイル}: {キーのパス}: {理由}` を出し、終了コード 2 で終わる |
| ポートが使用中 | 標準エラーにポートの番号と `DEV_DOCS_PORT` で変えられることを出し、終了コード 3 で終わる |
| プロンプトの YAML が無い・読めない・スキーマに違反する・描画できない | 標準エラーに `{ファイル}: {キーのパス}: {理由}` を出し、終了コード 4 で終わる |
| 設定の `version` がサーバーの読めるバージョンより古い | 警告のログに配信元の ID・設定のバージョン・サーバーが読めるバージョンを記録する |
| `alias_type` を持つ行の文書のエイリアスのキーが、alias-inject のスキーマに違反する | 警告のログに文書のパスと違反の内容を記録し、配信は始める。違反した文書は `search_docs` の `term`・`list_match_words` と本文のツールチップに載らない |
| `nav` の `auto` の条件がどの文書にも当たらない | 警告のログにタブと条件を記録し、配信は始める |

配信しなかった配信元を文書の MCP で指すと、違反したキーのパスと理由を返します。

## 設定を変えたら確かめる

配信元の `dev-docs.yaml`・スキーマ・検査と変換のスクリプトを変えたら、管理の MCP で確かめてから `reload` で配信に入れます。
サーバーの再起動は要らず、`/mcp` のセッションも切れません。

<!-- steps -->

1. `check_project` に配信元のパスを渡し、違反・無いパス・動かないスクリプト・設定のバージョンの新旧・索引の同期の件数を確かめる。
   エイリアスのキーの違反は文書のパスつきの違反で、どの文書にも当たらない `nav` の条件は警告で返る。
   ファイルに記載する前の設定は、`config` に中身を渡して確かめられる。
2. `try_convert` に配信元のパスと文書のファイルを渡し、配信するときと同じ変換の Markdown を確かめる。
   配信元のフォルダは変わらない。
3. `reload` で、変えた設定の配信元を配信に入れる。
   検証に失敗した配信元は外れ、`not_served` に理由が返る。
4. `describe` や `search_docs` で、変えた設定が出ることを確かめる。

<!-- /steps -->

Git 管理外の配信元は、`reload` を呼ぶまで変える前の設定で配信し続けます。
Git の配信元は、`default_ref` へ commit した後の要求から変えた設定で配信します（[Git のリポジトリを配信する](#git-のリポジトリを配信する)）。
スクリプトが 0 以外で終わると、`try_convert` が終了コードと標準エラーを返します。
引数と返す内容は [管理のMCP](../リファレンス/管理のMCP.md) にあります。

## 画面

サーバーを起動したら、ブラウザで `http://127.0.0.1:{port}/` を開きます（既定は `http://127.0.0.1:8781/`）。
`/` は配信中の配信元の先頭のトップへ移り、配信中の配信元が無ければ設定画面へ移ります。
使い方は [画面で読む](./画面で読む.md) にあります。
このサーバーは、画面が使う API（`/_api/` の入口）を配ります。

## 文書の MCP で読み書きする

文書の MCP は `/mcp` の 1 つで、配信元は引数 `source` で指します。
`source` を省くと、作業中の配信元を指します。

<!-- table: data -->

| やりたいこと | ツール |
| --- | --- |
| 使える配信元と種類を知る | `describe` |
| 検索・取得する | `search_docs` |
| 作成・更新する | `write_docs` |
| 削除する | `delete_docs` |
| 変更を確かめる | `list_changes` |
| 関連をたどる | `trace_related` |
| 用語の照合に使う語を引く | `list_match_words` |

<!-- /table -->

引数・既定値・上限・エラーは [文書の MCP](../リファレンス/文書のMCP.md) にあります。
どの作業場所からどの配信元を読み書きできるかは [配信元と権限](../はじめに/コアコンセプト/配信元と権限.md) にあります。
