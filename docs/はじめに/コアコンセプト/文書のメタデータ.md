# 文書のメタデータ

メタデータの置き場所・列名の対応・名前の既定・管理用の YAML の仕組み

## 共通のメタデータ

文書の種類によらず、検索・関連のたどり・画面は同じキーのメタデータを読みます。
共通のキーは `id`・`name`・`description`・`tags`・`main_tags`・`related`・`status` と、エイリアスのキー（`alias_type`・`aliases`・`command`・`cwd`・`url`・`avoid`・`skill`・`tool`・`path`・`port`・`replacement`）です。

文書 1 つのメタデータは、YAML の列の 1 か所だけに置きます。
Markdown・ソースコードは、管理用の YAML の `files[]` のその行に置きます。

文書の行（`documents[]`）の `metadata` は、共通のキーごとに読む列の名前を決めます。

```yaml
metadata:
  name: title
  description: meta.summary
```

入れ子の列は `meta.summary` のように `.` でつなぎます。
`metadata` に書かなかったキーは、同じ名前の列から読みます。

### オブジェクトの配列から取り出す

タグを `{name, main}` のオブジェクトの配列で持つ文書は、`[]` と `[{キー}]` で要素の値を取り出します。

```yaml
metadata:
  tags: tags[].name
  main_tags: tags[main].name
```

`tags[].name` は各要素の `name` を、`tags[main].name` は `main` が真の要素の `name` を、文字列の配列として読みます。
取り出した `tags`・`main_tags` は、`search_docs` の `filter`・`group_by`・`fields` で他の共通のキーと同じように使えます。
`main_tags` で絞ると、その文書の主なタグだけに当たります。

`write_docs` で `tags`・`main_tags` を書くと、オブジェクトの配列へ書き戻し、元の要素の `name`・`main` を崩しません。
書き戻し方は [文書のMCP](../../リファレンス/文書のMCP.md) の `write_docs` にあります。

## 共通のキー名で書く

`write_docs` は、`data`・`set` などに渡した共通のキー名を、`metadata` の対応で元の列に読み替えて書きます。
列名をそのまま渡しても、同じ列に書きます。
共通のキー名と、その列名を同じ操作に両方渡すとエラーです。

種類ごとの対応は、`describe(source, kind)` が表で返します。

## タグの付け方

タグは自由な文字列で、配信元はタグのマスターを持ちません。
エージェントには、文書の MCP の `instructions` で、次のタグの付け方を案内します。

```text
タグ:
- 付ける前に `search_docs` の `group_by="tags"` で使われているタグを見て、同じ意味のタグを使い回す
- 複合語は単語まで分けてタグにする（`エラー処理` は `topic:エラー` と `action:処理`）
- 動作は `action:`、題材は `topic:`、道具は `tool:` で始める
- 配信元にタグの規約があれば、`describe(source)` の説明書に従う
```

## 名前の既定

`name` が空の文書は、ファイル名から拡張子を除いた名前になります。
`records` の要素は `body_file` が指すファイルの名前で、`body_file` が無ければ文書の `id` です。
検索・関連のたどり・画面の API は、この既定を入れた後の `name` を読みます。

## 管理用の YAML

ソースコードなど YAML でない文書は、タグや概要文を自分では持てません。
管理用の YAML の `files[]` に 1 ファイル 1 行で記載すると、行ごとに 1 つの文書として配信されます。

```yaml
files:
  - path: a.py
    tags: [auth]
  - path: b.py
    name: 部品 B
```

文書の行は `records: files`・`body_file: path` で管理用の YAML を指します。
文書の `id` は `body_file` が指すファイルの拡張子を除いたパス（`src/a`）で、本文はそのファイルの内容です。
`files[].path` の値は、メタデータのキー `path` に入ります。

キーの一覧とスキーマ `templates/files.schema.yaml` は [設定](../../リファレンス/設定.md) の「管理用の YAML」にあります。

### 載せるファイルの判定

管理用の YAML には、次の除外の条件に当たらないファイルを 1 ファイル 1 行で載せます。

| 除外の条件 | 見分け方 |
| --- | --- |
| ベンダーのコード・生成物のフォルダ | パスの途中のフォルダ名が `vendor`・`third_party`・`generated`・`__generated__`・`dist` のいずれか |
| 生成物のファイル名 | ファイル名の末尾が `_pb2.py`・`_pb2_grpc.py`・`.min.js`・`.min.css`・`.map` のいずれか |
| ロック | ファイル名が `package-lock.json`・`pnpm-lock.yaml`・`go.sum`・`bun.lockb`・`npm-shrinkwrap.json` のいずれか、または末尾が `.lock` |
| バイナリ | 先頭 8192 バイトに NUL バイトがある |
| 再エクスポートや空の `__init__` | `__init__.py` で、中身が空か、import 文・先頭の docstring・`__all__` への代入だけ |

`.gitignore` は読みません。
プロジェクト固有の生成物は、文書の行の `exclude[]` で外します。

除外の条件に当たらないファイルのうち、テストには `tests` の関連（対象のコード）を、設計書と対応するコードには `implements` の関連（その設計書）を記載します。
`implements` はコード → 設計書、`tests` はテスト → コードの向きで、設計書 → コードの関連は記載しません。
設計書を実装するコードは、設計書を起点にした `trace_related` で引きます（[文書の MCP](../../リファレンス/文書のMCP.md) の `trace_related`）。

### ずれの検出

メタデータは、文書の列や管理用の YAML が変わるとずれます。
サーバーは起動時と読み直しのときに、次のずれを数えて警告のログに残し、配信は止めません。

| ずれ | 内容 |
| --- | --- |
| `metadata` の列の欠け | `metadata` に書いた列が無い文書。書いていないキーは数えない |
| 索引に無いファイル | 管理用の YAML のフォルダの配下で、`files[]` に記載されていないファイル。除外の条件に当たるファイルは数えない |
| ファイルが無い行 | `files[].path` が指すファイルが無い行 |
