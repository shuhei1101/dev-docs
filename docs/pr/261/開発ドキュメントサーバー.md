## 変更方針

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| スキーマの参照 | `project-index.yaml` の全ての設計書の行の `schema.ref` を `design-schemas/v8.4.0` へ上げ、全ての文書の検査に合格させる | v9 系は [#263](https://github.com/shuhei1101/dev-docs/issues/263) |
| 単体テスト（バック）の実行場所 | `runner`。手元でしか用意できないものを使用せず、外部のサービスへ実際に接続せず、Python と uv を workflow の中で入れられる | - |
| 結合テスト（バック）の実行場所 | `runner`。一時フォルダの配信元と、GitHub から clone する project-index・npx で取る mdmark の CLI を使用する。どちらも公開の配布元からの取得で、外部のサービスへの書き込みではない。git・Python・uv・Node 24 を workflow の中で入れられる | 判定フローチャートの注記の「workflow の中で入れられる道具」の公開の配布元からの取得に該当する |
| lint の実行場所 | `local`（判定フローチャートの lint の分岐） | - |
| lint の検査 | 既存の検査に、`.github/workflows/` への actionlint と、`uses:` の `{owner}/{repo}@{バージョン}` を `gh api repos/{owner}/{repo}/commits/{バージョン}` で参照して実在を確認する検査を追加する。どれかが失敗しても全ての検査を最後まで回す今の構造を保つ | 検査をスクリプトにするかはモジュール構成設計で決定する |
| テストを回す workflow | `workflow_dispatch` だけで起動し、入力で層（単体（バック）・結合（バック）・結合（フロント）・単体（フロント））と、結合テストのパス・並列数を受ける。結合テストのパスを省いたときは層の全件を回す。push・PR を契機にしない | インターフェース定義を先に作り、reviewer の合格を受けてから workflow のファイルを作る |
| ジョブのタイムアウト | 判定フローチャート『タイムアウトの決め方』で、層ごとの手元の全件実行の実測から決定する | 値はインターフェース定義設計で決定する |
| run_runner | `runner` の層に、テンプレート『テスト実行方法』の記載例と同じ呼び方（起動した実行を API で参照できるまで待ってから終わるまで待ち、失敗してもログを取得してから失敗で終える）で記載する | `run_all`・`run_one` は手元のコマンドのまま残す |
| workflow のテスト | インターフェース定義の `flows[]` ごとに、`tests/e2e/workflow/` へ gh で本物の GitHub Actions を起動するテストを作る（規約『GitHub Actions の workflow のテスト』）。テストは検証用のブランチを push するため手元で回す | テスト実行方法の層への記載方法はインターフェース定義設計で決定する |
| ランナーでの確認 | マージの前に、workflow の `on:` へ作業ブランチへの `push` を一時的に追加して push し、層ごとに成功と skip の件数を確認してから `push` を除外する | 規約『Git フックと CI で動かすもの』 |
| 費用 | public のリポジトリの標準ランナーで回し、料金は発生しない | - |
