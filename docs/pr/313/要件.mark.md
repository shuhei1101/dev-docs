# 要件

## 要望

dev-docs の画面に、配信元のメタデータを一覧で参照する画面と、画面で編集中の変更をまとめて直コミットする操作を加える。

| 要件 | 終了の条件 |
| --- | --- |
| メタデータの一覧 | 配信中の配信元ごとに、用語集・エイリアス・タグ・rule-inject の索引・配信元の設定（`project-index.yaml`）・管理用の YAML（`files.yml` など）を、種類ごとの表で参照できる |
| rule-inject の索引の一覧 | 索引の行ごとに、規約（ルールのファイル）と、その規約を適用するパス・ツール・引数が並ぶ |
| 編集中の変更 | 一覧の行の値（タグ・概要・関連・別名・用語・索引の行）を画面で修正・追加・削除し、送信する前の修正を一覧で確認できる。画面を開き直しても、送信していない修正が残る |
| まとめて直コミット | 編集中の変更を、配信元ごとに 1 回の送信で project-index の書き込みの API（`POST /sources/{source}/commits`）へ送信し、1 つのコミットにしてプッシュする。送信の前に差分確認（`dryRun`）の結果で差分を確認できる |
| 送信できない修正 | 直コミットを許可していない種類の修正・検査に合格しない修正・取得した後に他の変更で変わった文書への修正は、コミットせず、修正ごとに理由（許可を記載する端末の設定のキー・違反したキーと直し方・今のバージョン）を画面に出す |
| 直コミットの対象 | 直コミットの対象は、データとメタデータ（タグ・概要・関連・別名・rule-inject の索引・用語集）。規約の本文は行の追加と文言の修正だけを対象にし、テンプレートとスキーマは対象にしない |

`未確定`: 規約など、配信元の設定の `direct_commit.kinds[]` に入れると本文も直コミットできる種類の文書のメタデータを、画面からどこまで修正させるか（決める工程: 複合ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 画面のサーバーが、修正できる項目を種類ごとに決めたキー（メタデータのキーと、規約の本文の行の追加・文言の修正）に絞ってから書き込みの API へ送信する | project-index を変えずに、今の書き込みの API だけで進められる | 許可は種類の単位のため、エージェントの `write_docs` からは本文も直コミットできる |
| B | project-index に、種類ごとに直コミットできるキーを決める設定を加える | 画面とエージェントのどちらからも、同じ範囲だけを直コミットさせられる | project-index の修正を切り出し、その完了を待つ |

推奨: A

画面から送信する修正は画面が作るため、画面のサーバーで項目を絞れば要望の範囲に収まる。エージェントの `write_docs` の範囲は、配信元ごとに許可する種類を追加する後続で決められる。

`未確定`: rule-inject の索引を、どの経路で一覧・修正するか（決める工程: 複合ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 索引を持つ配信元の `project-index.yaml` に、索引を文書の種類として配信する行を加え、ほかのメタデータと同じ書き込みの API で修正する。行の `schema`・`validators[]` で、rule-inject の `write_index_entry` と同じ索引の検査（ルールのファイルの有無・glob の誤りなど）を通す | 画面のサーバーの経路が 1 つで済む。rule-inject はフックのたびに索引のファイルを読み込むため、直コミットの後の読み直しは要らない | rule-inject の索引のスキーマはパッケージの中にあり、検査を呼べる CLI も無いため、検査の手段（下の表）が要る。索引を持つ配信元（knowledge の `rules.yaml`・ai-monitor の `rules.global.yaml` など）の `project-index.yaml` に行を加える修正も、それぞれのリポジトリへ切り出す |
| B | 索引だけは rule-inject の MCP（`write_index_entry`）と同じ処理を経て書き込む | rule-inject の索引の検査・読み直しをそのまま使える | 画面のサーバーから rule-inject を呼ぶ経路が新たに要り、rule-inject の修正を切り出す |

推奨: A

ほかのメタデータと同じ編集中の変更の送信に乗るため、利用者の操作が分かれない。配信元の設定への行の追加と索引の検査の手段は、切り出した Issue の完了を待つ間も、ほかのメタデータを先に進められる。

案 A の索引の検査の手段は、次の表の A で進める。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | rule-inject に、索引の検査の CLI（`check_indexes` と同じ判定）とスキーマを、配信元の `validators[]`・`schema` から呼べる形で出す修正を切り出す | 索引の検査を rule-inject の 1 か所に保てる | rule-inject の修正の完了を待つ |
| B | 索引を持つ配信元が、それぞれ検査のスクリプトを持つ | rule-inject を変えずに進められる | knowledge・ai-monitor などで同じ検査を重複して持つ |

推奨: A

検査が配信元ごとに分かれると、rule-inject の索引の書式が変わるたびに全ての配信元を修正することになる。
