# 要件

## 要望

反映作業『dev-docs のサーバーの再起動』の待ちと判定が、`os.execv` で同じプロセスのまま起動し直したサーバーを新しいサーバーとして見分ける。

| 対象 | 終わりの条件 |
| --- | --- |
| 待ちのスクリプト `scripts/dev-docs-server-wait.sh` の `listening` | 指定した UNIX 時刻以後に起動し直したサーバーが 127.0.0.1:8781 で待ち受けたら `ok` で終わる。PID が変わらない再起動でも `ok` になり、指定した時刻より前から動き続けているサーバーでは `ok` にならない |
| 反映作業の実行スクリプト（#128・#130・#133 の `実行.sh` の `running_new`） | 修正したファイルの更新より後にサーバーが起動し直していれば `skipped`、起動し直していなければ再起動を要求する |
| #130 の確認スクリプト（`確認.sh`） | 修正したファイルの更新より後にサーバーが起動し直したかを、PID が変わらない再起動でも判定する |
| #130 の反映作業の確認方法（`index.yaml`） | 起動し直した時刻を、上と同じ値で観測する記載にする |
| 開発コマンドの設計書の `管理作業` | 起動し直した時刻の判定の仕方と、実際の再起動で確認した記録にする |

- 起動し直した時刻は、サーバーのログ（端末の設定の `log_dir`。既定は `~/.local/state/dev-docs/logs/dev-docs.log`）の、uvicorn が待ち受けを始めた行（`Uvicorn running on http://127.0.0.1:8781`）の最後の時刻で判定する
  - サーバーのコードとインターフェースを変えずにスクリプトだけで閉じる
  - ログは 5 MB で回転するため、回転した後のファイル（`dev-docs.log.1` など）も参照する
- 起動し直した時刻を求める処理は待ちのスクリプトに 1 つ持ち、反映作業のスクリプトはそれを呼ぶ
- マージの後、[#129](https://github.com/shuhei1101/dev-docs/issues/129) で #130 の反映作業『dev-docs のサーバーの再起動』を実行し直す

<details markdown="1">
<summary>起動し直した時刻の取り方の比較</summary>

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | ログの待ち受けを始めた行の時刻で判定する | スクリプトだけで閉じ、サーバーのコードを変えない | ログの書式とファイルの場所に依存する |
| B | 管理の MCP の `status` に起動し直した時刻を追加し、それで判定する | ログに依存しない | インターフェースとコードの変更とテストが加わる。`status` は読み込みの後に 200 秒を超えても応答しないことがある（#126） |

推奨: A

確認スクリプトは配信元の読み込みが終わった後に判定するため、B では `status` の遅さに該当する。

</details>
