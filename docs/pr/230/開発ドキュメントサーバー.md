## 変更方針

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| 性能（開き直し） | 配信元の設定・リビジョン・文書の一覧を同時に送信し、文書だけをその後に送信する。応答は dev-docs の中に控えない | 決定値は NFR-16（15 秒） |
| 性能（配信元ごとの最初の読み込み） | project-index が配信元ごとの最初の問い合わせで行うリビジョンの書き出しと文書の一覧の値の作成は、[shuhei1101/project-index#85](https://github.com/shuhei1101/project-index/issues/85) で扱う | dev-docs の側では速くできない |
| エラー返却 | 文書の取得全体に制限時間（NFR-15、60 秒）を置き、超えたら 503（`projectIndex.kind` が `timeout`）で打ち切る。project-index の 5xx は 502（`kind` が `failed`、理由は project-index の `detail`）にする | 問い合わせごとの 45 秒（NFR-14）だけでは、3 回順に待つと 135 秒まで延びる |

2 回目以降に開くときの短くし方は、案 B（問い合わせを同時に送信するだけにし、応答は持ち越さない）にした。
案 A（配信元の設定と文書の一覧の応答を、配信元と commit ごとに持ち越す）は、IF-155-10 の制約「dev-docs の中に控えない」（project-index が読み直した配信元と文書を、dev-docs を再起動せずに次の要求から返す）と合わない。

### 計測の結果

稼働中の dev-docs と project-index を止めずに、計測用に別のポートで project-index（develop の `006a490`）と dev-docs（develop の `abe2d81`）を、状態のフォルダを空にして起動した（2026-11-16）。
`dev-docs serve` は計測用の 1 つだけで、稼働中のものとはポートも状態のフォルダも分けた。
起動の直後に Issue の `dd2.cjs`（接続先だけ計測用に変えた）で 14 件の配信元を 2 回ずつ開き、画面側は Playwright の `requestfinished` で要求ごとの時間を、サーバー側は project-index への問い合わせごとの時間を取った。

- project-index は起動から 4 秒で待ち受けを始めたが、配信元の一覧に 2 秒以内に応答するまで 506.7 秒かかった
- jsDelivr の mdmark の読み込みは、どの回も 9〜65 ms だった。画面の時間の大半は文書の取得（`/_api/sources/{配信元}/docs`）だった
