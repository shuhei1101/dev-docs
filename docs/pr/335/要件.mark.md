# 要件

## 要望

文書の画面から、どの種類の文書の本文も編集して直コミットできるようにする。

- 文書の画面に編集のボタンを配置し、Markdown の文書と、種類ごとのスキーマを持つ YAML の文書の本文を編集できる
- YAML の文書は種類ごとの個別の対応を持たず、スキーマの型から編集の部品を選ぶ。本文の表に出ている値は、その表の上で修正できる
- 規約（`items[].body`）・プロンプト（`parts[].texts[]`。MCP の instructions・ツールの description を含む）・エージェントフロー・単語の対応表の行を、文書の画面から修正できる
- 編集した内容はメタデータの画面と同じ編集中の変更に溜め、同じ編集中のパネル・差分確認・コミットの確認を経て、配信元ごとに 1 つのコミットで project-index の書き込みの API へ送信する。検査に合格しない変更は、送信の前の差分確認で項目のパスと理由を出す
- 画面から編集できる範囲（配信元・種類）を設定で切り替えられる。既定は全ての配信元・全ての種類で編集できる
- [メタデータの取得](https://docs.shuhdev.com/dev-docs/docs/interface/IF-155-28.yaml?rev=develop)・[編集中の変更の直コミット](https://docs.shuhdev.com/dev-docs/docs/interface/IF-155-29.yaml?rev=develop) の、修正できるキーの種類ごとの絞り込みと「規約の本文・テンプレート・スキーマは画面から書き換えない」の記載を削除する
- 配信元の設定で `body: false` の種類の本文と、SQLite の表の行の種類は、project-index が書き込みを断るため、編集のボタンを出さない
- project-index の書き込みの API は `@body`・項目のパスへの `set`・`text_edits`・`replace` を既に受けるため、project-index の変更は要らない。設計で要ると分かったときは project-index の Issue として切り出す

`未確定`: 編集の方式（決める工程: 単一ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 文書の画面の `編集` で元のファイル（Markdown か YAML）をエディタで開き、ファイル全体を書き換える | 種類ごとの対応が要らず、Markdown を含む全ての種類で有効 | YAML の項目の位置を利用者が探す。表の上で修正する要望を満たさない |
| B | YAML の変換で各ブロックに元の項目のパスの目印を埋め、表示した場所でスキーマの型から選んだ部品で修正する | 表の上・本文の場所で修正でき、要望の「表の上で直接修正」を満たす | Markdown の文書と、目印を持たない部分は修正できない |
| C | A と B の両方を入れる | 全ての種類の全体の書き換えと、表示した場所での修正の両方を満たす | 作る量が最も多い |

推奨: C

要望が「どの種類の文書の本文も」と「表に出ている値はその表の上で修正」の両方を求め、利用者は段階に分けずに入れてよいとしているため。

`未確定`: 編集できる範囲の設定の持ち先（決める工程: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | project-index の端末の設定の `sources[].direct_commit.write_api_kinds` にある種類だけを編集できるようにする | 書き込みの API の許可と編集のボタンが 1 つの設定で決定し、仕組みが 2 つにならない | dev-docs の側だけで編集のボタンを止められない |
| B | dev-docs の端末の設定に配信元・種類の切り替えを持ち、`write_api_kinds` と両方にある種類を編集できるようにする | 書き込みの API の許可を変えずに画面の編集だけを止められる | 同じ質問に回答する設定が 2 つになる |

推奨: A

メタデータの取得の行ごとの `editable` が既に `write_api_kinds` で決定しており、同じ判定に合わせると設定が 1 つで済むため。
