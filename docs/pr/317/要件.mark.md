# 要件

## 要望

メタデータの画面の直コミットを、project-index の書き込みの API の衝突したときのブランチと項目ごとのバージョンで送信し、次を満たす。

| No | 要件 | 確認方法 |
| --- | --- | --- |
| 1 | ふだん（衝突しないとき）の直コミットは今のまま、既定のブランチへ 1 コミットでプッシュする | SC-155-15 の正常シナリオの期待値がそのまま満たされる |
| 2 | 編集の間に同じ文書のほかの項目（例: 概要）が書き換わっても、利用者が修正した項目（例: タグ）と重ならなければ衝突せずにコミットする | リモートの develop へ n1 の概要を変えるコミットをプッシュした後に n1 のタグの修正を送信すると、200 でコミットが 1 つ増え、n1 の概要はほかの変更の値、タグは利用者の値になる |
| 3 | 同じ項目が書き換わっていた・文書が削除されていたなどで衝突したときは、利用者の修正を、編集を始めたときのコミットからのブランチに残す。既定のブランチには何もコミットしない | 衝突したときの応答に残したブランチの名前があり、そのブランチの先頭のコミットが利用者の修正を持ち、リモートの develop にコミットが増えない |
| 4 | 衝突してブランチに残したときは、編集中の変更からその修正を除き、残したブランチの名前と、衝突したときのスクリプトが PR の URL を返却したときはその URL を画面に出す。利用者は手で解消しない | パネルに、ブランチの名前（と PR の URL）が出て、編集中の変更の件数が減る |
| 5 | 衝突したときのスクリプトが失敗した・指定が無いときも、ブランチに残したことと、スクリプトの結果（失敗の理由）を画面に出す | スクリプトの終了コードが 0 でないとき、パネルにブランチの名前と失敗したことが出る |
| 6 | 編集を始めたときのコミットがブランチの起点に使えない（クローンに無い・既定のブランチの祖先でない）ときは、今と同じく断り、編集中の変更を理由と一緒に画面に残す | 409（`BaseCommitUnusableError`）のとき、編集中の変更が残り、理由が出る |
| 7 | dev-docs 自身の文書のメタデータ（タグ・概要）を画面から直コミットできるよう、dev-docs の `project-index.yaml` に `direct_commit` を追加する | dev-docs のメタデータの画面で、許可した種類の行を修正・送信でき、develop に 1 コミット増える |
| 8 | 端末の設定の、書き込みの API から直コミットできる種類と衝突したときのスクリプトを、反映作業で登録する | 反映作業の確認方法のとおり |

編集を始めたときのコミットは、配信元ごとに、編集中の変更の最初の 1 件を追加したときのメタデータの取得の `baseCommit` を 1 つ記録し、送信のときに `baseCommit` に指定する（インターフェース定義設計で決定）。

項目ごとのバージョンは、送信のとき開発ドキュメントサーバーが変更ごとに文書の取得（リビジョンに `baseCommit`）で `itemVersions` を取得し、修正した項目のバージョンだけを `expected_version` の辞書にする（インターフェース定義設計で決定）。

衝突したときのスクリプトは、dev-docs の `scripts/` に配置し、ブランチのプッシュと PR の作成（`gh pr create`）をして、PR の URL を標準出力の最後の行に出す。ラベルは付けない。端末の設定の配信元の行から、このスクリプトを指す（ユーザーが決定）。

dev-docs の `project-index.yaml` の `direct_commit`（`branch: develop`）は、YAML の設計書の種類と管理用の YAML の種類の全てを許可する（ユーザーが決定）。
