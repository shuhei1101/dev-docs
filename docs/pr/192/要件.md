# 要件

## 要望

- `docs/flowchart/` の YAML のうち `visibility: public` の文書から、GitHub Pages の公開ページを生成する
- 2 文書（[新しく作るか修正するかの判定](https://github.com/shuhei1101/dev-docs/blob/864aae2/docs/flowchart/flowchart-new-or-modify.yaml)・[documentsの行の判定](https://github.com/shuhei1101/dev-docs/blob/864aae2/docs/flowchart/flowchart-documents-row.yaml)）を `visibility: public` にし、「使い方」の目次とサイドバーから開けるようにする
- 生成したページの判定フローの図（mermaid）は、今の公開ページの mermaid と同じく図として描かれる
- 生成したページの文書の ID への参照（`](id:flowchart-documents-row)`）は、公開ページどうしのリンクになる
- `develop` へ push するたびに、手で生成し直さずに公開ページが新しくなる

`未確定`: 公開ページのビルドの方式（決める工程: モジュール構成設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | GitHub Actions のワークフローで、生成のスクリプトが公開の YAML を Markdown にして `docs/` の中に書き出し、続けて Jekyll（`actions/jekyll-build-pages`）で今の AI Monitor のテーマのまま描いて配信する | 公開ページの見た目・URL・テーマの取り込み（[#74](https://github.com/shuhei1101/dev-docs/issues/74)）が今のまま。生成物を commit しない | Pages の設定の `build_type` を `workflow` へ切り替える反映作業が要る（管理者の権限） |
| B | legacy のビルドのまま、生成した Markdown を commit する（lefthook の pre-commit で生成し直す） | Pages の設定を変えない | 同じ中身の原本と生成物が 2 つ並ぶ。フックを実行しない commit で生成物が古くなる |
| C | knowledge の `pages.yml`・`build_pages.py` と同じく、mdmark の `build` で公開の文書を 1 枚の HTML にまとめて配信する | knowledge と同じ方式になる | 公開ページの見た目・URL が変わり、AI Monitor のテーマを使用しなくなる。Pages の設定の切り替えも要る |

推奨: A

公開ページの見た目と URL を変えずに、原本の YAML だけから公開ページを作れる。
A を選んだ場合、Pages の設定の切り替えを `反映作業/index.yaml` に記載し、実行者と時期をモジュール構成設計で決める。
