### #59 ER 図

- `x-diagram: er` の値を、mdmark の ER 図の部品（`<!-- er -->` の範囲の JSON。[mdmark#298](https://github.com/shuhei1101/mdmark/pull/298)）で出す。`erDiagram` の Mermaid は出さない
- 実体（`er.entities[]`）が `columns` を持たないときは、同じ文書のテーブル（`tables[]`）のうち `title`（論理名）が実体の `name` に当たるテーブルの `columns` から列を作る（共通の型 `er` の `columns` の説明「書かなければ、同じ設計書のテーブルのカラムから作る」のとおり）
  - aituber の ER 図の実体が空になる原因は、`er.entities[]` の多くが `columns` を持たず、列が `tables[].columns` にだけあること（aituber の `dev/設計書/ER図/キャラクター.yaml` で確認した）
- テーブルの位置（`x`・`y`・`w`）は変換が配置する（mdmark の ER 図の部品は自動で並べない）
- 関連の多重度（`||--o{` などの Mermaid の書き方）を、部品の両端の多重度（`1`・`0..1`・`1..n`・`0..n`）に読み替える
- 関連の両端の列（部品の `fromColumn`・`toColumn`。部品は省略を認めない）は外部キーから決める
  - 片方の実体の列のうち、外部キー（テーブルの列の `foreign_key.table`、実体の列の `key: FK` と `comment` の `参照: {実体}.{列}`）がもう片方の実体の列を指す列を外部キーの端、指される列をもう片方の端にする
  - 端の列が決まらない関連（列を持たない他の分類の実体への関連など）は図から除外し、図の元データの表にだけ残す
- 図の元データの表は、#90 の他の図と同じく既定で閉じる

### #91 引用符の維持

- 往復編集で読む `load_roundtrip` の時点で引用符の種類を保ち、`write_docs`・`delete_docs`・設定の移し替えなど `load_roundtrip`・`dump_roundtrip` を使う全ての書き込みで、変更していない項目の引用符（単一引用符・二重引用符・引用符なし）を元のまま書き出す
- 改行を含む引用符なしの文字列をブロックのリテラル（`|-`）で書く今の処理（`_represent_str`）は、引用符なしの文字列だけに当てる

### #97 本文の id: のリンク

- スキーマ駆動の変換が本文（Markdown の文字列の値）に出す `[名前](id:{文書の ID})` を、型 `ref` の値の `link_reference` と同じリンク先（同じ配信元の文書の相対パス）へ書き換える
- `[名前](id:{文書の ID}#{項目のパス})` は、リンク先の文書の項目の見出しへのアンカーを付ける。見出しにならない項目を指すリンクは、アンカーを付けずに文書を指す。型 `ref` の値の `link_reference` も同じアンカーを付ける
- どの文書の ID にも当たらないリンクは書き換えずに出し、警告は出さない
- コードブロック・行内のコードの中の `id:` は書き換えない

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| mermaid の `click` の `id:` のリンクを、フロー図のノードのリンクへ変換する | mdmark のフロー図のノードにリンクの項目が無く、[mdmark#310](https://github.com/shuhei1101/mdmark/issues/310) を待つため #97 から分けた | [#98](https://github.com/shuhei1101/dev-docs/issues/98) |
| mdmark の ER 図の部品を含むリリースを待つこと | 画面は jsDelivr の mdmark の `master`（v0.9.0）を読み込み、ER 図の部品は mdmark の `develop` にだけある。この PR の変換が出す `<!-- er -->` は、mdmark のリリースまで画面で図にならず JSON のコードブロックのまま出る。#90 の `wide=`（[確認ログ](../90/確認ログ.md)）と同じく、リリースを待たずにこの PR で出す（ER 図は今も Mermaid のまま画面で図にならず、出す前と比べて悪くならない） | [mdmark#298](https://github.com/shuhei1101/mdmark/pull/298) を含む mdmark のリリースが、このスプリントの release の E2E より前に要る（`正常シナリオ（ER 図を読む）` の E2E は、そのリリースまで fail する） |
| `converters[]` の出力と、Markdown の本文の文書（`.md`）の `id:` のリンクの解決 | #97 の入出力は文書の本文（Markdown の文字列の値）で、使う側の ai-monitor の設計書はスキーマ駆動の変換で描く。`dev/generated/` の Markdown 生成は ai-monitor が持つ | 予定なし |
| 表の外部キーのセルで、物理名で書いた同じ文書のテーブルを見出しへのリンクにする | `markdown.py` の `_foreign_key` がテーブル名を論理名だけで引き、物理名（ER図テンプレートの `foreign_key.table` は物理名・論理名を定めていない）で書いた外部キーが文字列のまま出る不具合。今回の要望に含まれない | [#104](https://github.com/shuhei1101/dev-docs/issues/104) |
| aituber の ER 図の設計書の `er.entities[].columns` の整理 | 配信元の YAML の修正で、この PR の変換（テーブルの列から作る）を前提にする | 予定なし（この PR の変換でテーブルの列から作るため、YAML の修正は要らない） |
