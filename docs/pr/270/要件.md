### タブとサイドバー（#229）

規約『開発ドキュメントのナビゲーション』に従い、`nav.tabs[]` を次の順で定義する。配信元に無いタブは置かない。

| 順 | タブ | 入れる文書 | サイドバーのグループ |
| --- | --- | --- | --- |
| 1 | はじめに | `docs/guide/` の `category: はじめに` | - |
| 2 | 使い方 | `docs/guide/` の `category: 使用方法` | - |
| 3 | 設計書 | 設計書の種類の行（アーキテクチャ図・非機能要件・シナリオ・インターフェース定義・モジュール構成・画面設計・部品設計・設定・外部API・外部ライブラリ・テスト実行方法・開発コマンド）・デザイン方針・モック | 種類（`group_by: kind` か種類ごとの `group`） |
| 4 | 規約 | 判定フローチャート | - |
| 5 | コード | `src/`・`frontend/`・`tests/` などの管理用の YAML の行 | サブシステムかフォルダの単位 |
| 6 | リファレンス | `docs/guide/` の `category: リファレンス` | - |

- 各 `auto` の `filter` に `not`（`kind` が `index`）を記載し、目次をタブとサイドバーに並べない
- 読む人が参照しない内部のファイル（`docs/pr/`・ロックファイル・スクリーンショットなど）はタブとサイドバーに並べない

`未確定`: モジュール構成（149 件）のサイドバーの分け方（決める段: ドキュメント修正）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `group_by: kind` で種類ごとに分け、モジュール構成の中は名前の順に並べる | 今の画面の機能で書け、種類が増えても設定を直さない | モジュール構成の中が 149 件の平たい一覧になる |
| B | モジュール構成をタグ（`main_tags`）でさらに分ける | 機能の単位でまとまる | `auto.group_by` で共通のメタデータを指定する [#251](https://github.com/shuhei1101/dev-docs/issues/251)（作業 PR #267）が入るまで書けない |

推奨: A

#251 を待たずに進められ、B は #251 が入った後に設定の書き換えだけで移れるため。

### 検索の対象とメタデータ（#257）

- 配信元のフォルダで `/project-index:setup` をもう一度実行し、Git 管理のファイルを推奨の範囲（`**/*`）で対象に入れる。管理用の YAML の置き場所と行は setup の結果に従う
- `docs/pr/` は検索の対象に入れない（project-index 自身の見直し [shuhei1101/project-index#132](https://github.com/shuhei1101/project-index/pull/132) と同じ）
- `content/prompts/` は setup が書くプロンプトの行の文書として配信する
- コードの行に設計書への `implements`、テストの行にコードへの `tests` を記載する（向きは project-index の `schemas/files.schema.yaml`）
- 終わりの条件は、`check_project` の索引の同期の件数（管理用の YAML に無いファイル・ファイルが無い行・`metadata` の列が無い文書）が 0 で、設計書から `trace_related`（`direction: in`）で実装とテストをたどれること
