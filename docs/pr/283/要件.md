# 要件

## 要望

公開ページの配信の workflow `.github/workflows/pages.yml` のインターフェース定義と、フローごとの E2E テストを作成する。

| 要件 | 終了の条件 |
| --- | --- |
| インターフェース定義 | `docs/interface/` に `entry.kind: trigger` の設計書があり、テンプレート『インターフェース定義』の workflow の書き方（`overall_flow`・`flows[]`・`test_file: tests/e2e/workflow/…`）で記載され、全ての文書の検査に合格する |
| 目次 | `docs/interface/index.yaml` に新規作成したインターフェース定義の行がある |
| E2E テスト | `flows[]` ごとに、`flows[].test` の名前のテストの関数が `tests/e2e/workflow/` にあり、規約『GitHub Actions の workflow のテスト』の手順で本物の GitHub Actions を起動して全て pass する |

`未確定`: 配信の job（`deploy`）を通る正常系のフローの E2E テストの起動のしかた（決める工程: インターフェース定義設計）

`deploy` の job は環境 `github-pages` を使い、配信できるブランチは `develop`・`gh-pages`・`master` だけ。
検証用のブランチで起動すると `deploy` は拒否され、develop で起動すると公開ページを配信し直す。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | E2E テストは検証用のブランチで起動し、`build` の job のフローと、`deploy` が環境の配信できるブランチの制約で拒否されるフローを確認する。配信が成功するフローは、develop への push の実行の結論を確認する | 公開ページを配信し直さない | 配信が成功するフローをテストから起動しない |
| B | 正常系のフローの E2E テストを develop で起動し、公開ページを配信し直す | 配信までをテストから起動して確認できる | テストのたびに公開ページを配信し直す（規約『ユーザー確認が必須な事項』の「外へ出る」に該当する） |

推奨: A

配信の成功は develop への push のたびに起きる実行で観測でき、テストのたびに外へ出る操作を発生させずに済む。
