# 要件

## 要望

スキーマ駆動の変換が、`x-diagram` の値を AI Monitor の新しいスキーマ（[shuhei1101/ai-monitor#3222](https://github.com/shuhei1101/ai-monitor/pull/3222)）のキーで参照し、mdmark の部品で描画する。
変換の対応は AI Monitor のインターフェース定義『設計書のMarkdown生成』の「図」の制約に統一する。

| 図の型 | 終わりの条件 |
| --- | --- |
| フローチャート（`flowchart`・`dataflow`・`architecture`）のノード | `kind` から mdmark のノードの種類を決める（`actor`・`external` → `external`、`process`・`system` → `script`、`store` → `data`、`start`・`question`・`action`・`result` は同じ値）。`kind` が無いノードは `process` として扱う。`hint` をノードの説明にする。`shape` からの推定をやめる |
| フローチャートの辺 | `line`（`flow`・`read`・`write`・`reply`・`loop`）を線の種類にし、無ければ `flow`。戻る線は今と同じく `loop`。`tip` を線の詳細にする |
| フローチャートの向き・枠 | `direction`（`TD`・`LR`）が無ければ、`flowchart` は `TD`、`dataflow`・`architecture` は `LR`。`frame`（`label`・`nodes`）を、中のノードを囲む mdmark の枠にする |
| 状態遷移 | 状態を `action` のノードにし、始点（`start`）から初期状態へ、終了状態から終点（`result`）へ線を描画する。`全状態` の元・`元の状態` の先は、`representative` の状態との 1 本にする |
| ER 図の関連 | `from_column`・`to_column` を両端の列に、`from_cardinality`・`to_cardinality` を両端の多重度にする。`cardinality`（Mermaid の記法）の読み替えと、外部キーからの両端の列の推定をやめる |

図の元データの表で隠す列（今の `id`・`shape`）は、新しいキーに合わせて見直す。
画面が参照する mdmark は今の `mdmark@master`（v0.10.0 と同じ commit）のままで、描画の確認もこのバージョンで行う。

`未確定`: 古いキー（`shape`・`subgraphs`・`cardinality`・Mermaid の線の記法の `line`）で記載した文書の扱い（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 新しいキーだけを参照する。`shape` は参照せずノードの種類の既定（`script`）にし、`cardinality` だけの関連は図から除外して元データの表に残す | 変換の対応が AI Monitor の生成と同じになり、推定の分岐が残らない | 配布物へ追従するまで、dev-docs 自身と他の配信元の古い文書の図で、ノードの種類と ER 図の関連の線が減る |
| B | 新しいキーを優先し、無ければ古いキーから今の推定で参照する | 追従前の文書の図が今と同じに描画される | 推定の分岐が残り、追従が済んだ後に削除する作業が要る |

推奨: A

古い文書は AI Monitor の新しいスキーマへの追従（変換 `v0.4.0.py`）で移行され、それまでも図は崩れずに出るため（ノードは既定の種類になり、関連は元データの表に残る）。
