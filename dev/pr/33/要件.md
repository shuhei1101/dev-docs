# 要件

## 要望

`dev-docs.yaml` の documents の行を「どのファイルを、どの種類として、どの列から読むか」の定義だけにし、文書の値を持たせない（Issue の D-171 の E）。
文書 1 つのメタデータは YAML の列（Markdown・ソースコードは管理用の YAML `files.yaml` のその行）の 1 か所だけに置き、`write_docs` で 1 つずつ直せるようにする。

<!-- table: data -->

| 対象 | 終わりの条件 |
| --- | --- |
| `documents[].type` | キーをなくす。documents の行は常に YAML を読み、`type` を書いた設定は起動時・`reload`・`check_project` の検証で違反になる |
| 直接 Markdown を指す行・フロントマター | 読み込み・書き込み・変更の一覧・試しの変換から Markdown の行の分岐とフロントマターの読み書きをなくす。Markdown・ソースコードは `records: files`・`body_file: path` の行（管理用の YAML）で読む |
| `documents[].metadata` | 値を「共通のキー → 列名」の文字列だけにする（`name: title`）。入れ子の列は `.` でつなぐ。書かないキーは同じ名前の列とみなす。`{type: ref, field: ...}`・`{type: custom, value: ...}` のオブジェクトは違反になる |
| `documents[].defaults[]` | キーをなくし、書いた設定は違反になる。メタデータを重ねる処理（`apply_defaults`）と、`related` が `defaults[]` 由来で外せないときの違反をなくす |
| `documents[].alias_type` | `metadata` から行の属性へ移す。値の選択肢とエイリアスの元の行の形は alias-inject のスキーマを正本にし、shuhei1101/alias-inject#37 と合わせる |
| `documents[].exclude[]` | 新しい形式のスキーマと読み込みでもそのまま使える（#26・PR #29 の挙動を保つ） |
| `write_docs` | `create`・`update`・`replace`・`delete`（項目）の `data`・`path` に共通のキー名（`name` など）を渡すと、`metadata` の対応を解いて元の列（`title` など）に書く。列名をそのまま渡しても同じ列に書く。対応の無い種類では今と同じ列に書く |
| `describe` とツールの説明 | `describe(source, kind)` の結果と `write_docs`・`search_docs` の説明に、種類ごとの共通のキーと列名の対応を出す。#28（PR #31）の記載を取り込んだうえで加える |
| `check_project` の索引の同期 | `missing_refs` を「`metadata` に書いた列が無い文書の件数」に読み替える（`ref` の判別子が無くなるため） |
| 配布用の JSON Schema | リポジトリの直下に `schemas/dev-docs.schema.json` を置き、サーバーが検証に使う `src/dev_docs/schemas/dev-docs.schema.yaml` と同じ内容にする。内容がずれていたら単体テストが落ちる |
| 設計書 | `dev-docs.yaml` のキーの一覧を設定の設計書として `dev/設計書/設定/` に置く |
| 雛形 `templates/dev-docs.yaml` | 1 行目に `# yaml-language-server: $schema=https://raw.githubusercontent.com/shuhei1101/dev-docs/{バージョンのタグ}/schemas/dev-docs.schema.json` を置き、`type` の行をなくす |
| `/dev-docs:setup` | `dev-docs.yaml` を作るときに 1 行目へスキーマの行を書く。既にある `dev-docs.yaml` の 1 行目にスキーマの行が無い、またはタグが dev-docs のバージョンと違うときは、書き換えを候補に示して了承後に書き換える |
| `dev-docs migrate`（配信元の設定） | 配信元の設定のバージョンを上げ、今の形式の `dev-docs.yaml` を新しい形式へ移し替える手順を持つ |
| 公開ドキュメント | 下の `## 更新ドキュメント` のページを新しい形式に合わせる |

<!-- /table -->

決定: 配布用の JSON Schema とサーバーが読むスキーマのどちらを正本にするかは A（モジュール構成設計で決めた）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `src/dev_docs/schemas/dev-docs.schema.yaml` を正本にし、`schemas/dev-docs.schema.json` は生成して commit する。一致を単体テストで確かめる | パッケージの組み立てを変えない | 同じ内容のファイルが 2 つになる |
| B | `schemas/dev-docs.schema.json` を正本にし、サーバーもそのファイルを読む | ファイルが 1 つで済む | パッケージにリポジトリの直下のファイルを含める設定が要る |

推奨: A

サーバーはスキーマをパッケージの中から読んでおり（`resources.files`）、読み方を変えずに配布のファイルだけを足せる。

決定: `dev-docs migrate` で機械的に移せない設定（`type: markdown` の行・`custom`・`defaults[]`）の扱いは A（インターフェース定義設計で決めた）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | migrate は機械的に移せる分（`type: yaml` の削除・`{type: ref, field}` を列名の文字列へ・`metadata.alias_type` を行の属性へ）だけを当て、移せない分は手順の結果に違反として並べて止める。移せない分は `/dev-docs:setup` が管理用の YAML の行へ移す | 値を利用者に確かめずに書き換えない | 移せない設定を持つ配信元は setup をもう一度流す |
| B | migrate が管理用の YAML を作り、`custom`・`defaults[]` の値を各行へ展開する | 1 コマンドで移し替えが終わる | migrate に setup と同じファイルの突き合わせを持たせることになり、glob で付けた値を利用者が確かめずに全ファイルへ書く |

推奨: A

管理用の YAML の行づくりは setup が範囲のファイルとの突き合わせと利用者の確認を持っており、同じ処理を migrate に重ねずに済む。
