## 要望

| Issue | 終わりの条件 |
| --- | --- |
| [#123](https://github.com/shuhei1101/dev-docs/issues/123) | サーバーを起動・再起動した直後でも、MCP の要求が Claude Code の MCP の呼び出しの時間切れより十分短く返る。起動直後の応答時間を測り直し、PR に記録する |
| [#126](https://github.com/shuhei1101/dev-docs/issues/126) | `status` が、読み込みの後も Claude Code の MCP の呼び出しの時間切れより十分短く応答する。応答時間を測り直し、PR に記録する |

- #123: 文書の MCP の要求は、全ての配信元の読み込みの終わりを待たずに応答する
- #126: `status` は、要求のたびに配信中の全ての配信元へ `check_sync` をかけずに応答する。遅い原因が `check_sync` の中（`walk_files`・`store.load`）にあるかは、設計で切り分ける
- 応答時間の決定値は、Claude Code の MCP の呼び出しの時間切れから逆算して非機能要件に記載し、計測のログを `dev/pr/136/テスト結果/` に配置する

`未確定`: 起動直後の文書の MCP の応答の仕方（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 要求が指す配信元（`source` か `cwd` から決まる配信元）の読み込みだけを待つ | レスポンスの中身が読み込みの後と変わらない | 読み込みの順番によっては、指した配信元の読み込みを待つ時間が残る |
| B | 読み込み済みの配信元だけで応答し、読み込み中の配信元があることをレスポンスに添える | 待たない | 読み込み中の配信元は一覧・検索の結果に出ない |

推奨: A

要求が指す配信元の結果が欠けると、エージェントが文書が無いと誤って判断するため。待つ時間は、配信元ごとに読み込み、指された配信元を先に読み込むことで縮める。
