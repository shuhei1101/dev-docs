確定している直し方:

- #58: 配布用のスキーマ `schemas/dev-docs.schema.json` とサーバーが検査に使う `src/dev_docs/schemas/dev-docs.schema.yaml` の両方の `nav_item.auto` に `group_by` の定義を追加し、2 つをそろえる。管理の MCP の `write_nav` と起動時の nav の検査も `folder` を受ける
- #66: 要素の数によらず `config` を配列で書く（端末の設定の読み込みは文字列を配列にし、E2E も配列を期待しているので、コードの側だけを合わせる）
- #67: 画面を mdmark v0.9.0 に合わせ、[#51](https://github.com/shuhei1101/dev-docs/pull/51) で決めた「jsDelivr の master から読んで自動で追従する」を保つ。原因が mdmark 側の不具合なら mdmark へ起票する。読む mdmark のバージョンを固定するのは、ユーザーの確認を取ったときだけ
- #73: `dev-docs files` を管理用の YAML の行ごとに 1 回ずつ呼び、その行の `exclude` だけを `--exclude` に渡す（行をまとめて 1 回で呼ぶと、他の行の `exclude` が当たる）

`未確定`: `group_by` のフォルダの指定の書き方（インターフェース定義は推奨の B で書いた。#58 の終わりの条件の文言が変わるので、設計のレビューの後にユーザーへ確認する）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `group_by: folder` と書き、`folder` を予約の値にする | #58 の終わりの条件のとおり | `folder` という項目を持つ文書の `group_by` がメタデータで束ねられなくなる |
| B | `group_by: '@folder'` のように項目のパスと重ならない書き方にする | `search_docs` の `@path`・`@matches` と書き方がそろい、項目名とぶつからない | #58 の終わりの条件の文言が変わるので、ユーザーの確認が要る |

推奨: B

今の `group_by` は項目のパスを受けており、予約の値を混ぜると同じ値が 2 通りに読める。

再起動の停止時間の縮め方（インターフェース定義設計で確定）: 端末の設定・ポート・プロンプトの YAML を確かめたら待ち受けを始め、配信元の読み込みと起動時の検査を待ち受けの裏で流す。配信元を使う要求は、読み込みが終わるまで接続を切らずに待たせる。

起動の区間ごとの計測（負荷のある端末で 2 回、配信元 8 つ）:

| 区間 | 1 回目 | 2 回目 |
| --- | --- | --- |
| import | 7.2 秒 | 7.9 秒 |
| 配信元の読み込み（`registry.reload`） | 89.8 秒 | 94.3 秒 |
| 起動時の検査（`check_sync` と `nav` の警告） | 145.6 秒 | 125.6 秒 |
| `build_app` | 0.6 秒 | 0.2 秒 |

配信元の読み込みの大半は `default_ref` から設定・スキーマを読む `git show` の 400 回余りの呼び出しで、検査だけを後へ回す案では約 95 秒の停止が残る。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 配信元を読んだら待ち受けを始め、起動時の検査を待ち受けの後に回す | 起動の順番の変更が小さい | 配信元の読み込みの約 95 秒は接続できないまま残る |
| B | 待ち受けの順番は変えず、検査と読み込みを速くする | 起動の順番が変わらない | 配信元と文書が増えるほど再び遅くなる |
| C | 待ち受けを先に始め、配信元の読み込みと検査を裏で流し、配信元を使う要求は読み込みが終わるまで待たせる | 接続できない時間が import とプロンプトの読み込みだけになる | 読み込みの間の要求は答えが遅れる |

推奨: C

#65 の終わりの条件は接続できない時間で、C だけが配信元の数によらずそれを縮める。
