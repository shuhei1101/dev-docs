# 要件

## 要望

束ねた 3 つの Issue の終わりの条件を満たす。

| Issue | 終わりの条件 |
| --- | --- |
| [#39](https://github.com/shuhei1101/dev-docs/issues/39) | `records` を持つ行の `schema` をファイル全体に当てるか 1 行ずつに当てるかが決まり、検査（読み取り・書き込み・`check_project`）・`templates/files.schema.yaml`・`/dev-docs:setup` の手順・設定の説明がそろう。setup が作る組み合わせで files の文書に `'files' is a required property` の警告が付かず、スキーマと `records` が食い違う組み合わせを `check_project` が検出する |
| [#45](https://github.com/shuhei1101/dev-docs/issues/45) | 文書の API の応答に本文のファイルのパス（`Document.body_path`）が含まれ、画面が本文の相対リンクをそのパスを基準に解決して、管理用の YAML の行の文書で「文書が見つかりません」にならない。対応する設計書がそろう |
| [#46](https://github.com/shuhei1101/dev-docs/issues/46) | `CONTEXT_TIMEOUT_SEC` が応答の時間を測って決めた値に伸び、`hooks.json` の `timeout` がそれより長い。session-context が遅くなる経路を調べて直し、打ち切ったときの文に打ち切った秒数が入る |

`records` を持つ行の `schema` の当て方: ファイル全体のスキーマとし、1 行ずつの検査・項目の一覧（`describe`・`search_docs` の絞り込み）には `properties.{records}.items` を取り出して当てる。
`check_project` は `properties.{records}.items` を取り出せない組み合わせを違反にする（インターフェース定義設計で案 A に決めた）。

本文の相対リンクの行き先の引き方: 画面は `body_path` を基準に解決したパスをそのまま文書の API に渡し、文書の API は画面のパスで当たらなければ、文書のファイルか本文のファイルのパスが同じ最初の文書を返す（インターフェース定義設計で案 A に決めた）。

`CONTEXT_TIMEOUT_SEC` は 11 秒、`hooks.json` の SessionStart の `timeout` は 18 秒（インターフェース定義設計で決めた）。
2026-10-31 に端末の配信元 5 件で 10 回ずつ測った応答の時間は、修正前が /mnt/c の配信元で 25〜70 秒、遅い経路を修正した試作で最大 7.3 秒（p50 は /mnt/c の配信元で 2.7〜5.0 秒、Linux のファイルシステムの配信元で 0.14 秒）。
最大を p99.9 として余裕 50% を乗せ、`hooks.json` の `timeout` は内側の待ちの合計 11.5 秒に 50% を乗せた（規約『資源の値の決め方』）。

session-context が遅い経路は、`check_sync` が文書の行ごとに `collect_files` で配信元のフォルダを全てたどり直すこと（14 行で 14 回）と、`walk_files` がフォルダごとに `os.path.islink` で `lstat` を呼ぶこと（/mnt/c で 1 回 5 ミリ秒）だった。
共有のロック（`documents/store.py` の `_lock`・`sources/registry.py` の `_reload_lock`）は長い処理の間は持っていない。
どう直すかはモジュール構成設計で決める。
遅い経路は配信元の読み込み（`features/sources`）ではないため、[#42](https://github.com/shuhei1101/dev-docs/issues/42) と同じ所は触らない。
