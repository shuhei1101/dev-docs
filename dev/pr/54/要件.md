# 要件

## 要望

束ねた 3 つの Issue の終わりの条件を満たす。

| Issue | 終わりの条件 |
| --- | --- |
| [#39](https://github.com/shuhei1101/dev-docs/issues/39) | `records` を持つ行の `schema` をファイル全体に当てるか 1 行ずつに当てるかが決まり、検査（読み取り・書き込み・`check_project`）・`templates/files.schema.yaml`・`/dev-docs:setup` の手順・設定の説明がそろう。setup が作る組み合わせで files の文書に `'files' is a required property` の警告が付かず、スキーマと `records` が食い違う組み合わせを `check_project` が検出する |
| [#45](https://github.com/shuhei1101/dev-docs/issues/45) | 文書の API の応答に本文のファイルのパス（`Document.body_path`）が含まれ、画面が本文の相対リンクをそのパスを基準に解決して、管理用の YAML の行の文書で「文書が見つかりません」にならない。対応する設計書がそろう |
| [#46](https://github.com/shuhei1101/dev-docs/issues/46) | `CONTEXT_TIMEOUT_SEC` が応答の時間を測って決めた値に伸び、`hooks.json` の `timeout` がそれより長い。session-context が遅くなる経路を調べて直し、打ち切ったときの文に打ち切った秒数が入る |

`未確定`: `records` を持つ行の `schema` の当て方（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 行の `schema` はファイル全体のスキーマとする。1 行ずつの検査・項目の一覧（`describe`・`search_docs` の絞り込み）には、スキーマの `properties.{records}.items` を取り出して当てる。`check_project` は、`records` の行のスキーマが `properties.{records}.items` を持たない組み合わせを違反にする | 今の `templates/files.schema.yaml` と、配信元が持つコピー（shuhdev-gateway の `schemas/files.schema.yaml`）をそのまま使える。ファイル全体の検査も通せる | 行の `schema` の意味が `records` の有無で変わる |
| B | 行の `schema` は 1 行のスキーマとする。`templates/files.schema.yaml` を今の `files.items` にし、setup の手順と設定の説明をそれに合わせる。`check_project` は、スキーマが最上位で `records` の名前を必須にする組み合わせを違反にする | 行の `schema` の意味が `records` の有無で変わらない | 既にコピーを持つ配信元の差し替えが要り、破壊的変更になる |

推奨: A

配信元のコピーを差し替えずに警告が消え、モジュール構成『検査』の `DocumentChecker.check` の「`records` の行は要素を検査する」とも、取り出した 1 行のスキーマを当てることで食い違わない。

`未確定`: 本文の相対リンクの行き先が管理用の YAML の行の文書のときの引き方（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 画面は `body_path` を基準に相対リンクを解決したパス（例 `docs/b.md`）をそのまま文書の API に渡す。サーバーの文書の探し方（`find_page`）は、画面のパスで当たらなければ、そのパスを本文のファイルに持つ文書を引く | `try_convert`（`features/admin/service.py`）の `relative in (document.path, document.body_path)` と同じ引き方になる。画面は解決の基準を替えるだけで済む | 同じ本文のファイルを複数の行が持つと、最初の文書に当たる |
| B | 画面が、解決したパスから文書の画面のパスを求める（nav や API で本文のファイルのパスと画面のパスの対応を引く） | サーバーの探し方を変えない | 画面が対応表を持つ必要があり、API の応答が増える |

推奨: A

解決の基準の修正と、サーバーで既に使っている引き方の流用だけで閉じ、応答に足す項目が `body_path` の 1 つで済む。

`未確定`: `CONTEXT_TIMEOUT_SEC` と `hooks.json` の `timeout` の値（決める段: インターフェース定義設計。session-context の応答の時間を測り、規約『資源の値の決め方』で決める）

session-context が遅くなる経路の調べ方は、#46 の受付判断のレビューの指摘のとおり、`/mcp/` も同じ時刻に打ち切られていたことから、共有のロック（`documents/store.py` の `_lock`・`sources/registry.py` の `_reload_lock`）を持ったままの長い処理を先に調べる（決める段: モジュール構成設計）。
遅い経路が配信元の読み込み（`features/sources`）なら、[#42](https://github.com/shuhei1101/dev-docs/issues/42) と同じ所を触るため、先にマージされた方に合わせて取り込む。
