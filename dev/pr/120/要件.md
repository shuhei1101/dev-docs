# 要件

## 要望

作業範囲の外の配信元（`ref` に `default_ref` を持つ読む場所）への `search_docs`・`describe`・`trace_related`・`list_changes` で、1 回の要求の中の同じ `ref` の解決とスキーマの読み込みを 1 回にする。
配信元 `ai-monitor`（1,467 文書）への次の 3 つの要求が、Claude Code の MCP の呼び出しの時間切れより十分短く返る。

| 要求 | 修正の前（2026-11-08 の計測） |
| --- | --- |
| `filter`: name に `planner` を含む・`limit: 3` | 56.1 秒 |
| `view: count` | 85.3 秒 |
| `filter`: body の正規表現 `(?i)changelog`・`limit: 5` | 53.8 秒 |

- 1 回の要求の中では、`ref` を commit へ解決する git の起動を、読む場所ごとに 1 回にする（文書の数に比例させない）
- ブランチ名の `ref`（`default_ref` の `develop` など）は、要求をまたいで新しい commit を指しうるため、次の要求では解決し直す
- 作業範囲の中の配信元（`ref` が無い読む場所）の結果と応答時間は変えない
- 修正の後に、上の表と同じ 3 つの要求で時間を測り直し、計画書の `## テスト結果` に記録する

設計で決めた内容（モジュール構成設計）:

| 論点 | 決めた内容 | 理由 |
| --- | --- | --- |
| 解いた commit の持たせ方 | 読む場所 `Target` に `commit` を持たせ、権限と作業場所の『読む場所の解決』と画面の読む場所が作るときに 1 回だけ解く。文書のストアは `commit` を使い、無いときだけ解く | 要求をまたいで commit を控えないので、`default_ref` に入った新しい commit は次の要求から有効になる |
| リビジョンのスキーマのキャッシュ | `(repo_root, commit, スキーマのファイルの repo_root からの相対パス)` で控え、ファイルの `stat` とリビジョンの書き出しをしない。ファイルの日時のキャッシュのキーにも配信元の `root` の `repo_root` からの相対パスを加える | commit のファイルは書き換わらない。同じリポジトリの `root` の違う配信元を取り違えない |
| 応答時間の決定値を非機能要件に記載するか | 記載しない。退行は文書のストアの単体テスト（文書ごとの `row_schema` で git を起動しない）で検出し、修正の前後の時間は計画書の `## テスト結果` に記録する | 遅さの原因は git の起動の回数で、回数を数えるテストで決定値の計測より確実に検出できる。Claude Code の MCP の呼び出しの時間切れの値には公式の出典が無く、決定値を逆算できない |
