# 要件

## 要望

メタデータに `id` を持たない文書の ID を、拡張子付きのパスにする。
同じフォルダに同じ名前で拡張子の違うファイル（`plan.ts`・`plan.js`・`plan.css`、`index.md`・`index.yaml` など）があっても、それぞれが別の ID の文書になる。

- 1 ファイルの文書の ID は、配信元の直下からのファイルのパス（拡張子付き。例 `design/repo.yaml`）にする
- `records` の要素で `body_file` を持つ行の文書の ID は、`body_file` が指すファイルの配信元の直下からのパス（拡張子付き。例 `src/a.py`）にする
- `records` の要素で `body_file` を持たない行の文書の ID は、`{管理用の YAML のパス（拡張子付き）}#{位置}` にする
- `loader.py` の `_stem` で拡張子を除いて ID を作る処理を無くす。表ごとに ID の作り方を指定する設定は追加しない
- メタデータの `id` を持つ文書の ID と、`name` が空の文書の `name`（ファイル名から拡張子を除いた名前）は変えない
- `related[].to` が配信元のどの文書の ID にも当たらない行を、`check_project` の `sync` で知らせる（種類の名前は `unresolved_related`。要素は `{行の id}: {文書の id}: {to}`）
- 当たらない `related[].to` の照合は、配信元の全ての文書の ID の集合を 1 回だけ作って行う
- 起動時は `sync` の他の種類と同じく警告のログへ出し、`status` の `sources[].sync` に件数を出す
- setup のスキルが `tests` の関連に書く `to` を、拡張子付きのパスにする
- 単体・結合・E2E の全件が pass する

`未確定`: 別の配信元を指す `related[]`（`source` を持つ行）を検査の対象にするか（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `source` を持たない行だけを照合し、`source` を持つ行は数えない | 配信元 1 つの文書の ID だけで照合でき、検査の時間が配信元の数で増えない | 別の配信元の ID の書き誤りは見つからない |
| B | `source` を持つ行も、その配信元の文書の ID と照合する | 別の配信元への関連の書き誤りも見つかる | 別の配信元の文書を読み込む必要があり、その配信元が配信されていない端末では照合できない |

推奨: A

`check_project` は配信元ごとの検査で、別の配信元が同じ端末で配信されているとは限らないため。

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| 既にある管理用の YAML の `related[].to` を拡張子付きに書き換える `dev-docs migrate` の手順 | 書き換え先が shuhei1101/ai-monitor の `files.yml` だけで、利用者が手で書き換える（task-reviewer が合格とした扱いの判断） | 予定なし |
| コメント・ビュー・既読など、文書の ID をキーにした控えの移し替え | 正式な利用の前で、移し替える控えが無い（ユーザーの回答） | 予定なし |
| shuhei1101/ai-monitor の `files.yml` の `related[].to` の書き換えと、`exclude` から `src/` の `*.css`・`docs/` の `index.md` を外すこと | ai-monitor のリポジトリの作業で、この作業 PR のマージを前提にする | 起票予定 |
