## 要望

文書の画面・設定画面・見つからない画面を、knowledge の React の規約（shuhei1101/knowledge#79・shuhei1101/knowledge#80）の構成で、最初から React の 1 つの SPA として作る。
PR #12 の画面設計とモック（commit `6d2fded` で固定したリンク。起点 Issue の `## #3 との関係（決定）`）を参考にし、そこで決めた要素と ai-monitor の `dev_docs` から移す機能を消さずに再現したうえで、デザインは shadcn/ui・Tailwind に合わせて整える。
決定の正本は起点 Issue の `## 必読` に並ぶ話し合いのフォルダのファイル（`decisions.yaml` の D-n・`docs/` の A-n・L-n）で、着手前に読む。

`未確定`: 画面をサブシステムとして分けるか（決める段: 複合ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | アーキテクチャ図に `画面`（scope `frontend`）のサブシステムを追加し、開発ドキュメントサーバーは画面のビルドを配るだけにする | 言語・ランタイム（TypeScript・ブラウザ）とテスト（Vitest・Storybook・Playwright）がサーバーと分かれて読める | サブシステムの増加はアーキテクチャ図の決まりでユーザーへ確かめる |
| B | 画面を開発ドキュメントサーバーの一部として扱う | アーキテクチャ図を変えない | 1 つのサブシステムに Python と TypeScript のランタイムが混ざる |

推奨: A

画面はサーバーと別に単体・結合・Storybook で確かめられ、独立してテストできる単位に当たる。

`未確定`: ビルドした画面の配り方（決める段: モジュール構成設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | ビルドの成果物を commit せず、導入・更新（クローンでの `uv sync` の後）で `frontend/` をビルドする | 生成物を commit しない | 利用者の端末に Node が要る。導入・更新のシナリオにビルドの失敗の扱いが増える |
| B | ビルドの成果物を commit し、サーバーはそのまま配る | 利用者の端末に Node が要らず、導入・更新の手順が変わらない | 画面を直すたびにビルドの差分が commit に入る。ビルドの漏れを検査で防ぐ要がある |

推奨: B

導入・更新は今クローンでの `git pull` と `uv sync` だけで済んでおり、利用者の端末の前提を増やさずに済む。ビルドの漏れは lefthook とテストで検出できる。
