# 要件

## 要望

### #44 画面を mdmark#222 の機能につなぐ

文書の画面（`frontend/`）を、[shuhei1101/mdmark#222](https://github.com/shuhei1101/mdmark/issues/222)（mdmark の [#280](https://github.com/shuhei1101/mdmark/pull/280)）で入った `mount` の入出力につなぐ。

| mdmark の機能 | 画面での使い方 |
| --- | --- |
| `mount` の `baseMarkdown`・`update(markdown, {baseMarkdown})` | URL に `base` があるとき、比較元の本文から変わった箇所を本文で強調する。`base` を外したら `null` で強調を解除する |
| `onColumnsChange` | 表の列の出し入れを受け、画面の API の表の列の設定の保存（`view-put_columns`）を呼ぶ。mdmark の内部の DOM（`.mdmark-columns-menu` のチェックボックス）を参照する今の方式は削除する |
| `commentStore.update`・`remove` | コメントの修正・削除をコメントの置き場所へ反映する |
| `reloadComments`・`focusComment` | パネルで修正・削除した後に本文のマーカーを描き直し、パネルのコメントの場所から本文の該当箇所へ移動する。印を探してスクロールする今の方式（`findCommentMark`）は削除する |

読み込み元は jsDelivr の `mdmark@master` のまま変えず、mdmark#222 を含むリリースが mdmark の master に入るのを待つ（[#51](https://github.com/shuhei1101/dev-docs/pull/51) のリリースに追従する決定を保つ）。
画面の結合テストは、そのリリースが master に入った後に確定する。

終わりの条件（#44 の本文から写す）:

- 画面（`frontend/`）で、`mount` の `baseMarkdown` による比較元からの変更箇所の強調、`onColumnsChange` で受けた表の列の出し入れの保存（`view-put_columns`）、`commentStore.update`・`remove` によるコメントの修正・削除、`reloadComments`・`focusComment` によるマーカーの描き直しと本文の該当箇所への移動が動き、対応する設計書が合っている

### #94 ほかの配信元のスキーマをリビジョンを指定して参照する

`dev-docs.yaml` の文書の表（`documents[]`）の `schema:` で、ほかの配信元のスキーマを配信元の ID・パス・リビジョン（タグ・commit）で指せるようにする。

| 項目 | 内容 |
| --- | --- |
| 参照の書き方 | 配信元の ID・パス・リビジョンを持つオブジェクト（例: `schema: {source: knowledge, path: schemas/design/interface.schema.yaml, ref: v1.4.0}`） |
| 読む時点 | 指定したリビジョンのファイルを読む。参照先の作業ツリーの今の内容は読まない |
| 使う所 | 検査（`write_docs`）・`describe(source, kind)`・描画（`features/view/nav.py` の `$ref` の解決を含む）・スキーマ同士の `$ref` の解決（同じ配信元の同じリビジョンの中で解決する） |
| 誤り | 配信元・パス・リビジョンが見つからないときは、設定の検査（`check_project`・起動時の検証）で `documents[{番号}].schema` の違反にする |
| 既存の相対パス | 文字列の `schema:` は今の書き方のまま配信元の root からの相対パスとして読む |

参照先の配信元が `not_served`（検証で外した・`enabled: false`）でも、端末の設定に行があり Git のリポジトリなら、そのリポジトリから指定したリビジョンのファイルを読む。
端末の設定に無い・Git のリポジトリでないときは、参照する側の行の違反にする。

終わりの条件（#94 の本文から写す）:

- `dev-docs.yaml` の `schema:` で、ほかの配信元のスキーマを ID・パス・リビジョンで指せ、検査（`write_docs`）・`describe(source, kind)`・描画・`$ref` の解決がそのリビジョンのファイルを使う。見つからないときは設定の検査で誤りとして示し、既存の相対パスもそのまま使える
- 完了したら後続の [shuhei1101/ai-monitor#3188](https://github.com/shuhei1101/ai-monitor/issues/3188) に着手できる旨をコメントし、`確認:task-planner` を付ける

### #96 write_docs の違反に該当キーのスキーマの説明を添える

`write_docs` が検査（スキーマ）で弾いたときの違反に、違反したキーのスキーマの `title`・`description`・`x-rules`・`examples`・`x-bad-examples` を添える。

- 添えるのは違反した項目の分だけで、スキーマの全文は返さない
- スキーマにそのキーが無い項目は添えない（`x-rules`・`x-bad-examples` は [shuhei1101/knowledge#172](https://github.com/shuhei1101/knowledge/issues/172) の後に出る）
- 既存の `path`・`rule`・`fix` は変えない

添える項目は `write_docs` の応答を組み立てるときに `features/write` の中で添え、全ツールが共有する `shared/errors.py` の `Violation` は変えない。

終わりの条件（#96 の本文から写す）:

- `write_docs` の違反に、違反したキーのスキーマの `title`・`description`・`x-rules`・`examples`・`x-bad-examples` が違反した項目の分だけ添えられ、スキーマの全文は返さない
