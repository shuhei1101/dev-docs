# 要件

## 要望

`content/prompts/` に置いたプロンプトの YAML（スキーマは knowledge の `schemas/prompt.schema.yaml`、キーは A-42）を、dev-docs の文書の画面で読めるようにする。

| 要件 | 終わりの条件 |
| --- | --- |
| プロンプトの YAML（標準入力）から Markdown（標準出力）を出す変換を dev-docs が持つ | 各配信元が変換のスクリプトを書かずに、documents の行の `converter` で指して使える |
| 見出し | `name`・`kind`・`lang`・`description` が本文の頭に出る |
| 変数の表 | `vars` の入れ子（`items`・`properties`）を `traits[].name` のようなパスで展開し、型・必須・例・説明・出どころを 1 つの表に並べる |
| 「テンプレート」のタブ | 部品ごとに `id`・`role`・`when` の見出しと Jinja2 の本文が出る。本文の `{{ 変数 }}` に、説明・型・例のツールチップが付く |
| 例のタブ | 「既定の例」（各変数の `example`）と `examples[]` の組ごとに、`when` が真の部品だけを描画した結果のタブが出る。`kind: llm` は `role` ごとのメッセージに分ける。使わなかった部品と字数を出す |
| 言語の切り替え | `parts[].texts[]` の言語を切り替えて表示し、トップレベルの `lang` の言語に「注入」のマーカーを付ける |
| 描画できない組 | 未定義の変数・型の合わない値の組は、そのタブにエラーを出し、他のタブは描画する |
| 字数の注意 | `kind: hook` の描画結果が 1,000 字を超えたタブに注意を出す |
| setup の候補 | `/dev-docs:setup` が、配信元の直下とプラグインのルートの `content/prompts/` を見つけたら、documents の行（`paths`・`schema`・`converter`・`metadata`）を候補に出す |
| `metadata` の対応 | `name`・`description`・`tags` を共通のキーへ、`kind` を種類の列へ対応づける |
| 完了条件 | A-42 の例 1（`kind: hook`）と例 2（`kind: llm`）を配信し、画面で変数の表・テンプレート・例のタブ・言語の切り替えが出る。`/dev-docs:setup` で `content/prompts/` を持つリポジトリの documents の行が作られる |

`未確定`: 例の組の見せ方（決める段: PoC 検証の後のユーザーの確認）

mdmark（v0.8.0）はタブの入れ子を描けず、「テンプレート」・例のタブや例の組のタブの中に言語のタブを置けない（[reviewer の再現](https://github.com/shuhei1101/dev-docs/pull/56#discussion_r4430567991)）。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 変数の表・「テンプレート」・例をタブではなく `##` のセクションで並べる。例の組と「テンプレート」の部品を `###` のセクション（例の組の 2 つ目以降は閉じた状態）にし、セクションごとに言語のタブを置く | 今の mdmark で描け、言語のタブは同じ `group` で揃って切り替わる | 「テンプレート」と「例のタブ」がタブではなく開閉するセクションになる |
| B | 例と言語の組を 1 レイヤーのタブに平らにする（`既定の例 / en`・`既定の例 / ja（注入）` など） | 例をタブのまま保てる | 組 × 言語でタブが増え、スマホ幅で並びきらない。言語だけを揃えて切り替えられない |
| C | mdmark にタブの入れ子を追加する Issue を起票し、対応を待つ | 要件どおりの見た目 | 別リポジトリの変更待ちで、この PR が止まる |

推奨: A

今の mdmark で描け、言語の切り替えを揃える要件も満たせる。

`未確定`: 変換の置き場所と配信元からの呼び出し方（決める段: インターフェース定義設計）

`converters[].run` は配信元の直下を作業ディレクトリにして動き、dev-docs のクローンの `templates/` は配信元の外にある。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 変換を dev-docs のパッケージに置き、CLI のサブコマンドとして呼ぶ。`templates/` には `converters[]` と documents の行の雛形を置く | 配信元にコピーが残らず、dev-docs の更新で変換も新しくなる。Jinja2 は dev-docs の依存で済む | Issue の「`templates/` に変換を置く」と置き場所が変わる |
| B | 変換のスクリプトを `templates/` に置き、setup が配信元へコピーする | Issue の記述どおり | コピーが古くなる（#39 と同じ問題）。Jinja2 を各配信元の環境で用意する |

推奨: A

D-194 の目的（各リポジトリが変換を書かずに済む）を満たしたまま、コピーの古さと依存の用意が起きない。

`未確定`: documents の行の `schema` の指し方（決める段: インターフェース定義設計）

今の `documents[].schema` は配信元の直下からのパスだけを読み、URL は読まない。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | setup が knowledge の `schemas/prompt.schema.yaml` を配信元の `schemas/` へコピーし、行はそのパスを指す | 今の `schema` の読み方のまま。`files.schema.yaml` と同じ扱い | コピーが古くなる |
| B | `schema` に URL を書けるようにし、dev-docs が取得して控える | knowledge の更新に追従する | 配信の起動時にネットワークが要る。`schema` の読み方を変える |

推奨: A

D-194 の「変えたいプロジェクトだけコピーして自作する」とも合い、配信元ごとのスキーマを同じ置き場所で扱える。

`未確定`: 「`kind` を種類の列へ」の受け皿（決める段: 単一ユースケース設計）

共通のキーに種類のキーは無い（`id`・`name`・`description`・`tags`・`related`・`status` とエイリアスのキー）。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | setup が `nav` の `auto` に `group_by: kind` を付けた候補を出し、サイドバーを種類ごとにまとめる | 今の `nav` の書き方で、画面の並びに `kind` が使える | 検索の絞り込みには使えない |
| B | 共通のキーに種類のキーを追加する | 検索・画面の両方で使える | 全ての種類の文書に効く変更になる |

推奨: A

A-42 の `kind` の説明は「本文の書き方の検査と画面の並びに使う」で、画面の並びに使えれば足りる。

| 項目 | 理由 | 対応予定 |
