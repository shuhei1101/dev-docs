# 要件

## 要望

`write_docs` の検査で、スキーマで Markdown と宣言したキーの値を mdmark の点検（`mdmark check --text`）に通し、警告が 1 件でもあれば何も書き込まずに、警告をキーのパスつきの違反として返す。

- 警告の内容は、mdmark の描画時の「書き方の警告」と同じ文言にする
- `dry_run: true` でも同じ点検を当て、警告を返す
- `atomic: false` では、警告のあった操作だけを失敗として添字つきで返し、他の操作は書き込む（他の検査の違反と同じ扱い）
- mdmark（Node）を呼ぶ外部プロセスの呼び出しを `src/dev_docs/integrations/` に新設する

`未確定`: Markdown と宣言したキーの見分け方（決める工程: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | JSON Schema の `contentMediaType: text/markdown` を持つキーを Markdown とみなす | JSON Schema 2020-12 の標準のキーワードで、独自の `x-` を増やさない | 今のスキーマの `$defs/markdown` に宣言を追加するまで点検が効かない |
| B | 独自の `x-markdown: true` を持つキーを Markdown とみなす | `x-heading`・`x-shape` と同じ流儀で読める | 独自のキーワードが増える |

推奨: A

標準のキーワードで表せるものに独自の `x-` を作らないため。

`未確定`: 点検する値の範囲（決める工程: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 操作で変えたキーの値だけを点検する | 既に警告を含む文書でも、関係の無いキーの `update`（`tags` の追加など）が通る | 変えていないキーの警告は残る |
| B | 文書の Markdown のキーを全て点検する | 書き込んだ文書に警告が残らない | 既に警告を含む文書は、どの `update` も警告を直すまで拒否される |

推奨: A

既存の文書の警告の修正を、関係の無い書き込みの前提にしないため。

`未確定`: 外部プロセスの起動の単位（決める工程: モジュール構成設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `write_docs` の 1 回の呼び出しで点検する値をまとめ、外部プロセスを 1 回だけ起動する | `operations` の件数に起動の時間が比例しない | mdmark の CLI が複数の値を 1 回で受けられない場合は、受け方を mdmark へ依頼する必要がある |
| B | 点検する値ごとに外部プロセスを起動する | 今の `mdmark check --text` のまま呼べる | 値の数だけ Node の起動の時間がかかる |

推奨: A

書き込みのたびに Node を起動するため、件数に比例させないほうが応答が遅れない。

`未確定`: mdmark の CLI が無い端末・制限時間を超えたときの振る舞い（決める工程: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 点検せずに書き込み、点検できなかった理由を応答に添える | mdmark を入れていない端末でも書き込みが止まらない | 点検されないまま書き込まれる |
| B | 何も書き込まずにエラーを返す | 点検されない値が書き込まれない | mdmark を入れていない端末では Markdown のキーへの書き込みが全て止まる |

推奨: A

点検は書き込みの補助で、mdmark を入れていない端末での書き込みを止めるほどの理由が無いため。

`未確定`: mdmark の CLI の場所と制限時間の持ち方（決める工程: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 端末の設定にキーを追加して CLI の場所を持ち、制限時間は既存の `script_timeout_sec` を使う | 端末ごとに mdmark のクローンの場所が違っても指せる | 端末の設定のキーと `dev-docs:global-setup` の手順が増える |
| B | `PATH` の `mdmark` を使い、制限時間は既存の `script_timeout_sec` を使う | 設定のキーが増えない | `npm link` などで `PATH` に入れる手順が端末ごとに要る |

推奨: B

mdmark は npm のレジストリに公開しない CLI で、どちらの案でも端末ごとの用意が要り、設定のキーを増やさないほうが端末の設定の移し替えが要らないため。

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| AI Monitor のテンプレート `共通.schema.yaml` の `$defs/markdown` への Markdown の宣言の追加 | AI Monitor のリポジトリの変更で、この PR で決める宣言の書き方を前提にする | 起票予定 |
| 既に警告を含む既存の文書の修正 | 要望に含まれない。点検する値の範囲を案 A にすると、警告は変えたキーの書き込みのときにだけ問われる | 予定なし |
| `YAMLを直接編集した` の流れ（エディターで直接編集した YAML）への点検 | `write_docs` を通らない書き込みで、要望に含まれない | 予定なし |
